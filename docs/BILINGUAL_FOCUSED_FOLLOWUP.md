# 关键问题复测与验收分级（2026-09-28）

本轮按用户要求调整门槛：不影响主要理解和操作的小瑕疵进入待优化清单，不再单独导致验收失败。不得把已知的核心事实错误改名为“小瑕疵”来放行。

| 等级 | 判定 | 处理 |
| --- | --- | --- |
| 阻断 | 主要条件说反、输入输出或转换方向错误、错误处理与资源行为误述、核心操作无法完成 | 修正后定向复测 |
| 阻断 | 零基础稿整体由未解释术语构成，读者无法知道代码的用途和主要动作 | 改善主要解释后复测 |
| 非阻断 | 个别措辞不够自然、标题偏技术、段落略长、少量术语可进一步解释，但主要动作与结果仍清楚 | 记录改进，不因此追加付费调用 |
| 非阻断 | 省略与主要用途无关的内部细节，且没有作出相反或误导的陈述 | 允许省略 |

## 这轮调整

- 长稿以关键事实、前后段落一致性、包装函数实际返回值和清理边界为复核重点。
- 中英文零基础稿按用途分组，不要求每个辅助函数各占一段；允许保留必要事实而略超建议篇幅。
- 段落自动密度提示只处理明显过长的段落，篇幅本身不作为语义准确率或发布失败依据。
- 对直接连接官方 deepseek-flash、源码超过 200 行或 12000 字符的长稿，首次生成与复核均使用有预算上限的思考模式，避免错误草稿主导后续复核。每个应用请求仍为两次模型调用，可能增加模型耗时和用量。
- 其他兼容服务及平台赠送额度仍沿用各自支持的参数和限制；本轮结果不证明这些通道具有相同效果。

## 复测范围

仅 Zod parse.ts 和 CPython contextlib.py 两份既有源码。首轮修改提示规则后运行 8 个中英文／零基础／标准组合，发现同步和异步错误处理的概括仍有问题；随后调整首次生成方式，再运行同两份源码的 8 个组合。两轮合计 16 次应用请求，没有扩展源码集合，也没有重跑全部 40 份样本。历史结果保留，不能以成功的旧结果替代新失败。

源码只作静态分析，未执行。没有改变源码字节、提交或许可清单。此轮未修改产品 UI，不复测安装器、OAuth、云同步，也不合并或发布。
